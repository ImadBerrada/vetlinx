# Product implementation and roadmap

Applied on 2026-10-06 following the authorized product/architecture proposal. This is a delivery record and an ordered implementation plan; planned items are not advertised as working features.

## Product structure

One identity can act as a professional, pet owner, and organization member. Personal workspace selection never grants permissions. A persistent labelled workspace switcher exposes both personal profiles, with setup links for a missing profile. Organization and reviewer workspaces are authorized independently.

The professional navigation is Home, Profile, Credentials, Jobs, Applications, and Portfolio/CV. The owner navigation is Home/Pets, Find a clinic, Appointments, and account settings. Clinic staff have an appointment intake/queue inside their authorized organization workspace. Progressive onboarding requests only information needed for the next action; authentication preserves a safe return path to the selected clinic.

Every actionable screen must explain its current state and next step, retain inputs after errors, distinguish loading from empty results, and provide keyboard focus and mobile layouts. A directory lists only facts actually recorded by verified opted-in organizations. No invented ratings, availability, recommendations, clinical claims, or dashboard metrics are used.

Shared navigation fills the viewport instead of capping the application width. Desktop users can collapse the full-height sidebar to an icon rail; the preference persists across pages and reloads. Workspace selection expands the rail to keep profile and organization names readable. At mobile/tablet widths, navigation becomes a scrollable drawer with focus containment, Escape/close controls, trigger focus restoration and background scroll locking. Resizing across the breakpoint resets the drawer. A notification bell opens updates without expanding the header; dismissal failures retain the update. Public home, clinic discovery, workspace selection and owner setup share a full-width header.

## Architecture that supports further implementation

Keep the current Next.js BFF, NestJS modular monolith and PostgreSQL schema ownership. Domain modules own their records and state machines. Other modules use public application interfaces; the platform worker orchestrates those interfaces and owns delivery leases, not owner/clinical mutations. Do not split into network services until measured operational needs justify the extra failure modes.

Authentication checks account status, account authentication version and an active refresh-session family on each protected request. Login, refresh, recovery and session revocation share an account-row lock. Recovery tokens are random, hashed, purpose-bound, expiring, single-use and explicitly submitted. Email links carry token fragments, which browser forms remove from history before user interaction. Queued message bodies are encrypted; delivered/cancelled content is purged. A stable separately managed encryption key is required in production.

MFA password authentication issues a five-minute opaque hashed challenge rather than a session. Authenticator steps and hashed recovery codes are single-use; failures share an account-level lockout. Enrollment, step-up and disabling recheck the current family under the account lock. Production privileged routes require MFA and proof within 15 minutes. Refresh preserves the original proof timestamp, and password recovery preserves enrollment. Encryption includes a purpose-bound context for authenticator secrets.

Appointment commands own history and optimistic proposal versions. Transactional audit/outbox/in-app notices accompany state changes. Request snapshots preserve the consented owner/pet/clinic information and scheduled service/duration at submission. Slot locks serialize capacity allocation; a hold is consumed in the same transaction as appointment creation. Only unexpired/unreleased/unconsumed holds and requested/confirmed appointments occupy places. Proposed times remain separate from the authoritative appointment and keep its original capacity until acceptance atomically rechecks and moves to another published slot of the same service. Existing flexible appointments retain their workflow and are not automatically assigned slots.

Appointments owns optional clinic resources and immutable slot assignments. Each time block reserves every selected room, equipment item or care-team label exclusively across services, independent of its 1–10 appointment places. Touching intervals are allowed. These labels do not establish practitioner identity or licensing. Closing a time preserves reservations; an owner/admin can explicitly release them only from a closed, future time without active holds or requested/confirmed visits. Reopening rechecks active resources and conflicts before reacquiring all reservations atomically. Retirement is versioned and blocked while any upcoming or ongoing reservation remains. Organization management locks serialize creation/reopening/retirement against bookings and holds; audit failure rolls the command back. Resource names and assignment identifiers stay out of public availability and owner booking responses. Existing slots receive no automatic assignments. Limits are 50 resources per clinic and 10 per time block.

The delivery worker runs separately from API instances. It handles only explicitly supported event names/versions and uses transactional local consumer acknowledgement. Unsupported events remain pending for future handlers. Email transport is at-least-once: a crash after SMTP accepts but before the database acknowledgement can cause a duplicate; stable Message-IDs and idempotent queue keys reduce duplication but cannot promise exactly-once external delivery. Reminders are deduplicated per appointment/time and unsent reminders are cancelled when their appointment becomes stale. A cancellation concurrent with an already-started external send cannot retract email.

Web refresh coordination is currently scoped to one process. Shared refresh coordination is a prerequisite for multiple web replicas. Clinic appointment mutations acquire a public organization-policy interface inside their transaction. Shared locks keep the verified clinic/hospital and owner/admin/staff grant stable through commit; a previously committed suspension, role change or removal prevents the command.

2. **Reliable care coordination:** facility/branch access, staffed hours, individual practitioner availability and assignments, recurring schedules, waitlists, care-team delegation and pet ownership transfer with consent. Service catalogue, dated slots, shared room/equipment/care-team reservations across services, bounded capacity, expiring holds, check-in/no-show and owner-requested rescheduling are implemented. Release evidence: facility/practitioner permission and conflict tests and a real clinic scheduling pilot; local resource/capacity concurrency, timezone/DST and permission-race cases support the implemented workflow.
3. **Professional growth:** sourced/versioned licensing pathways with curators/reviewers, explainable eligibility/checklists, deadlines and renewals; verified provider publication, course/session enrolment, progress, assessment, attendance, issuer-verifiable certificates and CPD ledger. Release evidence: one jurisdiction approved by qualified domain owners and a provider running real learning. Preserve historical pathway/credential versions.
4. **Commercial capability:** validated entitlements/plans, paid course/verification purchases as approved, checkout/invoices/refunds/tax, webhook idempotency and reconciliation, support disputes, organization subscriptions and partner payouts where the business model requires them. Release evidence: jurisdiction/pricing/refund/payment ownership agreed and reconciliation tested. No payment vendor or financial flow is silently selected.
5. **Clinical platform:** minimal encounter with patient/consent/facility/practitioner provenance, signed records and amendments, prescriptions versus dispensing, diagnostic orders/results, imaging references, surgery/anaesthesia/critical-care workflows, stock linkage and interoperability adapters. Release evidence: clinical governance, privacy boundaries, provenance, correction and pilot support approved. Owner notes never become verified clinical facts automatically.
6. **Growth and intelligence:** consented messaging, saved searches/favourites, governed reviews, education/library/events, referrals, native apps and partner commerce as validated. Outcome analytics require explicit metric definitions, safe cohorts and sufficient data. Epidemiology/AI require de-identification, source provenance, quality evaluation and professional oversight before activation.

Each increment needs a persona/outcome, permission policy, state model, data classification, operational owner and acceptance evidence. Extend existing modules where they own the concept; create learning/licensing/billing/clinical modules only with those contracts. The detailed [phased backlog](phased-backlog.md) remains the domain catalogue.

## Railway deployment — 2026-10-06

The user-selected Railway production environment now runs web, API, worker and PostgreSQL, with persistent database and private evidence volumes. The public site is [web-production-c7d10.up.railway.app](https://web-production-c7d10.up.railway.app). Service settings and later release commands are documented in the [Railway deployment guide](../operations/railway-deployment.md).

The user explicitly approved paid Railway usage and requested email remain disabled. `MAIL_TRANSPORT=disabled` is an explicit production mode on API and worker: new email is not queued, eligible older mail is cancelled with content purged, and verification/recovery requests report unavailability without issuing recovery tokens. Registration, sign-in, both profiles, MFA and in-app worker tasks remain active. Unverified email addresses are not automatically verified.

Both production Docker images build. The deployment increment passed web/API lint, 26 API unit tests and 35 identity/worker integration cases. Live HTTPS checks verified registration, secure HttpOnly session cookies, professional and owner profile creation on the same account, pet creation, logout/re-login, private-route protection, public clinic directory access, foreign-origin rejection and explicit disabled-email responses. Cloud checks confirmed 23 applied migrations, API UID 1000, writable private storage, a fresh successful worker heartbeat and zero email queue records. Only the exact temporary deployment fixtures were removed; local test accounts were not copied into production.

The deployment also fixes production web builds that previously included browser tests importing API-local packages, and uses `VETLINX_PUBLIC_ORIGIN` to enforce the external HTTPS origin behind Railway's TLS proxy. Forwarded host headers cannot override that configured origin. Sources are connected to GitHub; the latest web release was triggered explicitly from source. Automatic deployment webhooks and operational backup/alert schedules require separate verification before being relied upon.
